Project Overview — What, Why, How

🎯 What is this project?

This is an autonomous software quality system that takes a GitHub repository URL as input and produces ready-to-merge pull requests that fix real bugs — with zero human effort in between.

You give it: a GitHub repo URL + your API keys.
It gives you: actual GitHub PRs with working code fixes, confidence scores, and root-cause explanations.

🤔 The Problem It Solves
  • Manual code review is slow and misses cross-file bugs
  • Static tools (Bandit, ESLint) only find syntax-level issues
  • LLMs hallucinate fixes without verifying them
  • Nobody creates PRs automatically from bug reports
✅ What Makes This Different
  • Cross-file reasoning — tracks how a bug in file A affects files B, C, D
  • Verified fixes — patches pass AST + test + security gates before PR
  • Surgical edits — never rewrites whole files; minimal diffs only
  • Confidence score — every PR has a 0–100% trust rating

🔁 The 30-Second Elevator Pitch (memorise this for interviews)

"I built a 10-agent pipeline that clones a GitHub repo, builds a dependency knowledge graph using Python AST, then uses Claude AI in a two-stage triage-then-confirm approach to find real bugs. For each bug it traces the cross-file blast radius, generates a surgical SEARCH/REPLACE patch, validates it through 4 gates — AST syntax, tests, regression, security — scores confidence across 5 signals, and opens an actual GitHub pull request. The whole thing runs in about 2 minutes."

Data Models — The Language of the System

Every piece of information flowing between agents is a Pydantic model in backend/models.py.

Finding — the fundamental unit

Finding(
  id          = "a3f9b2c1"   # 8-char UUID, stable across agents
  issue_class = "functional_bug"  # or security_vulnerability|performance|code_quality
  severity    = "high"        # critical > high > medium > low > info
  title       = "SQL injection via unsanitized user input"
  file_path   = "backend/utils/db.py"
  line_number = 42
  tool_source = "llm"         # who found it: llm | bandit | repo_mapper:ast

  # Set by Bug Hunter Stage B (Sonnet confirm pass):
  root_cause     = "Missing parameterization in execute()"
  evidence       = "Line 42: cursor.execute(f'SELECT * WHERE id={uid}')"
  suggested_fix  = "Use cursor.execute('SELECT... WHERE id=?', (uid,))"

  # Set by Bug Investigation Agent:
  blast_radius   = 3          # number of files affected if this file changes
  impact_paths   = [["db.py","orders.py","api.py"]]  # HOW it propagates
  related_tests  = ["tests/test_db.py"]
  similar_past_fixes = [...]  # from ChromaDB memory
)
PatchResult
Output of Code Generation. ok=True means all SEARCH/REPLACE edits applied and sanity check passed (change ratio < 60% of file). Can contain multiple FilePatch objects for cross-file fixes.
ValidationResult
4 gates: gate_1_ast_valid, gate_2_tests_passed, gate_3_no_regressions, gate_4_security_clean. Also tracks tests_available — if no test suite, confidence is capped at 60%.
ConfidenceScore
5 weighted signals summed to 0–1. Score ≥ 0.70 → auto-merge eligible. Score < 0.70 OR is_critical_path=True → PR is drafted (needs human approval).
PipelineJob
The master object passed through the entire orchestrator. Contains all events, findings, repair plan, validation results, and pull requests. Stored in st.session_state["last_job"] for UI re-rendering.

Pipeline Status Flow

PENDING → CLONING → PHASE_1_DISCOVERY → PHASE_2_INVESTIGATION → PHASE_3_PLANNING → PHASE_4_FIX_VALIDATE → PHASE_5_PUBLICATION → COMPLETED (or FAILED / CANCELLED)

Knowledge Graph — The Core Engine

The KnowledgeGraph (backend/knowledge_graph.py) is the most important component in the project. It is a NetworkX DiGraph that represents the entire repository as a graph of files, functions, classes, API endpoints, and database models, connected by typed edges.

Node Types

Node TypeExample IDWhat it represents
Filebackend/utils/db.pyEvery source file in the repo
Functionbackend/utils/db.py::execute_queryEvery function/method defined in Python files
Classbackend/utils/db.py::DatabaseEvery class
ServiceBoundarybackendTop-level directories (domain grouping)
APIEndpointAPI:/users:GETFastAPI/Flask/Django routes
DBModelDB:UserORM models queried in code
ConfigVarCFG:DATABASE_URLos.environ.get() keys

Edge Types

Edge TypeDirectionMeaning
IMPORTSconsumer → dependencyFile A imports module from File B
CALLScaller function → callee functionFunction A calls function B
TESTStest file → production filetest_db.py tests db.py
DEFINESfile → function/classFile owns this symbol
BELONGS_TOfile → service boundaryFile is in this top-level directory
SERVES_APIfile → API endpointFile exposes this route
QUERIES_DBfunction → DB modelFunction queries this ORM model

The 4 Build Passes

1

Pass 1 — Structure (os.walk)

Walks every directory. Creates File nodes and ServiceBoundary nodes. Records language (by extension), file size, which boundary the file belongs to. Skips: .git, venv, node_modules, __pycache__.

2

Pass 2 — AST (Python + C/C++)

For Python files: ast.parse() → indexes all functions, classes, imports, function calls. Syntax errors are recorded as findings (not silently skipped). Builds _file_by_module index so import utils.db maps to the real file node. For C/C++: regex extracts #include "local.h" edges. Adds TESTS edges for files named test_*.py.

3

Pass 3 — Framework

Regex patterns extract: FastAPI routes (@app.get("/path")), Flask routes (@app.route), Django URLs (path("url")), ORM queries (Model.objects.filter()), config variable usage (os.environ.get("KEY")).

4

Pass 4 — Dynamic Confidence

Marks edges with confidence: CALLS/QUERIES_DB edges that were resolved via imports get confidence="high"; unresolved dynamic calls get confidence="low".

🔥 Blast Radius — The Key Algorithm

Question: "If I change db.py, which other files could break?"

File dependency edges point from consumer → dependency. Impact travels in the reverse direction: if orders.py imports db.py, then a change in db.py can break orders.py.

db.py (changed) ↑ IMPORTS orders.py (direct dependent — affected) ↑ IMPORTS payments.py (direct dependent — affected) ↑ IMPORTS api.py (transitive dependent — affected via 2 hops) blast_radius("db.py", hops=2) → {"affected_files": ["orders.py","payments.py","api.py"], "file_count": 3, "category": "narrow", "related_tests": ["tests/test_db.py"]}

Category thresholds:

  • narrow ≤ 2 files affected
  • moderate 3–8 files affected
  • wide > 8 files — careful review advised
Interview tip: "The blast radius tells us the SCOPE of a bug's impact. A security vulnerability in a utility function imported by 20 files has a wide blast radius and gets flagged as CRITICAL PATH — it requires human approval before merging."

The 10 Agents — Deep Dive

The orchestrator runs all 10 agents in sequence. Each agent emits PipelineEvent objects via a callback, which appear live in the Streamlit feed.

AGENT 01
🗺️ Repo Mapper
phase_1_discovery

What it does: Builds the KnowledgeGraph (all 4 passes). Also converts actual Python syntax errors discovered during AST parsing into Finding objects (severity=HIGH). Detects circular import chains using networkx.simple_cycles().

Input: repo path on disk, repo name
Output: KnowledgeGraph object + list[Finding] (syntax errors, circular deps)

Why syntax errors are findings: ast.parse() will fail if a file has a syntax error. Rather than crashing, the error is captured with exact line+message and added as a HIGH severity functional_bug. The file is then excluded from further AST analysis (but is still in the graph as a node).

AGENT 02
📦 Dependency Analyzer
phase_1_discovery

What it does: Analyzes external dependencies (pip packages, npm modules). Checks for outdated/vulnerable packages. Enriches the graph with package dependency information.

Input: repo path, KnowledgeGraph
Output: Additional findings about vulnerable/outdated dependencies

AGENT 03
🔬 Static Analysis
phase_1_discovery

What it does: Runs traditional static analysis tools if available: Bandit (Python security), ESLint (JavaScript). Converts tool output into Finding objects.

Windows note: Bandit and ESLint are often not installed. The agent checks with shutil.which() and gracefully returns an empty list if tools are missing. This is why the LLM Bug Hunter exists — it's the fallback when static tools aren't available.

AGENT 04
🔍 LLM Bug Hunter
phase_1_discovery

What it does: Finds REAL bugs using a two-stage LLM pipeline. This is the most important discovery agent — it's what actually finds functional/security/performance bugs that static tools miss.

Stage A — Triage with Haiku (cheap)

For each source file, sends the numbered source code + graph context (what imports this file, what it imports) to claude-haiku. Asks it to return a JSON array of candidate issues: class, severity, line number, and a one-sentence "why".

POST to Haiku: "File: db.py\n{graph_context}\n{numbered_code}\n
List ONLY genuine defects as JSON..."
← [{"class":"security_vulnerability","severity":"high","line":42,
    "title":"SQL injection","why":"f-string in execute()"}]

Stage B — Confirm with Sonnet (strong)

For files that had candidates, sends the full file + candidate list + related file content (dependencies/dependents from graph) to claude-sonnet. Asks it to verify each candidate and discard false positives. For real bugs, it must provide: description, evidence, root_cause, suggested_fix.

POST to Sonnet: "File: db.py\n{candidate_list}\n{related_files}\n
For EACH candidate, decide if it is REAL. Return confirmed only..."
← [{"class":"security_vulnerability","severity":"high","line":42,
    "evidence":"cursor.execute(f'SELECT ... {uid}') at line 42",
    "root_cause":"No parameterization; uid from user input is interpolated directly",
    "suggested_fix":"cursor.execute('SELECT... WHERE id=?', (uid,))"}]

File selection priority:

Files are ranked by graph in-degree (how many other files import this file) + size. Most-connected files are analyzed first because bugs there have the widest blast radius.

Why two stages?

Haiku costs ~$0.001/file for fast triage. Sonnet costs ~$0.015/file for deep verification. By using Haiku first, we only send files with real candidates to Sonnet — saving ~80% of LLM cost on a typical repo.
AGENT 05
🧭 Bug Investigation
phase_2_investigation

What it does: For each confirmed finding, enriches it with cross-file impact data from the knowledge graph and searches ChromaDB for similar past fixes.

Steps per finding:

  1. kg.analyze_change(file_path) → direct/transitive dependents, impact paths
  2. kg.blast_radius(file_path) → file count, service boundaries crossed, related tests
  3. kg.trace_data_flow(file_path, line_number) → upstream callers, downstream callees
  4. ChromaDB: query for semantically similar past fixes in this repo
  5. If no root_cause yet (Sonnet Stage B didn't set one): call LLM to generate root cause using all the graph context above

Key output fields set on Finding: blast_radius, affected_files, impact_paths, direct_dependents, related_tests, affected_modules, similar_past_fixes

AGENT 06
📝 Repair Planner
phase_3_planning

What it does: Takes the list of enriched findings and produces a RepairPlan — a dependency-ordered list of RepairPlanItems, one per epicenter file.

Grouping logic:

Multiple findings in the same file → one RepairPlanItem. This means one code-gen call fixes all bugs in a file together (fewer LLM calls, no conflicting edits).

Ordering logic:

Files that are dependencies of other files must be fixed first. Example: if db.py imports utils.py and both have bugs, fix utils.py first — its fix may change the interface that db.py uses. This ordering uses topological sort on the dependency graph.

Prioritization:

  • Security vulnerabilities → first (highest risk)
  • Critical/high severity before medium/low
  • Wide blast radius before narrow
AGENT 07
🩹 Code Generation
phase_4_fix_validate

What it does: Generates the actual code patch for a file using claude-sonnet with a strict SEARCH/REPLACE format. Can produce cross-file patches (fixing the root cause in a dependency file, not just the symptom in the caller).

What gets sent to the LLM:

  1. All findings for this epicenter file (issue class, severity, line, description, root_cause, suggested_fix)
  2. The full source of the primary file (with line numbers)
  3. Related files from the knowledge graph (dependencies + dependents, up to 20KB each)
  4. A strict system prompt (_EDIT_INSTRUCTIONS) explaining the SEARCH/REPLACE format

System prompt key rules (memorise these):

  • Every block MUST have a ### FILE: path prefix
  • The SEARCH text must match EXACTLY (verbatim including indentation)
  • SEARCH must be unique — if it matches in 2 places, the edit is rejected
  • Fix at root cause if possible — edit a dependency file if that's where the bug lives
  • Never delete or weaken existing test assertions
  • Output NOTHING except ### FILE: lines and the SEARCH/REPLACE blocks

Retry logic:

If the patch fails (SEARCH not found, sanity check fails), regenerate_with_error() is called with the error message fed back to the LLM so it can correct itself. Up to validation_max_retries=3 attempts.

AGENT 08
✅ Validation Agent
phase_4_fix_validate

What it does: Validates a patch by applying it to a sandbox copy of the repo and running 4 sequential gates. The real working tree is untouched until the PR Author writes the final commit.

Gate 1 — AST Syntax

Every changed .py file is run through ast.parse(). If any file has a syntax error, the patch is rejected immediately. C/C++ files run through gcc -fsyntax-only if a compiler is available.

Gate 2 — Tests + Bandit

Finds test files for the changed files (e.g. test_db.py for db.py) and runs pytest -x scoped to those files. Also runs Bandit on all changed Python files if installed. Passes if both succeed (or if tests/bandit are unavailable — those just don't contribute to confidence).

Gate 3 — Regression Suite

If validation_run_full_suite=True (default), runs the entire test suite to check for regressions anywhere. Otherwise runs tests for all files in the blast radius.

Gate 4 — Security

Handled by the separate Security Verifier agent (see below).

No test suite? If the repo has no tests, gates 2 & 3 are effectively skipped and tests_available=False. The patch is still published (gate 1 AST must pass), but the confidence score is capped at 60% — which forces human approval.
AGENT 09
🔐 Security Verification
phase_4_fix_validate

What it does: Runs Bandit specifically on the patched files (in the sandbox) to check that the fix didn't introduce new security issues. Sets gate_4_security_clean on the ValidationResult. If Bandit isn't installed, the gate is marked unavailable (not failed).

This is the only agent that can block a fix that passed tests — a patch that resolves a functional bug but introduces a security vulnerability is rejected here.

AGENT 10
🚀 PR Author
phase_5_publication

What it does: Creates the GitHub pull request. This is the only agent that modifies the real working tree and interacts with GitHub.

Steps in order:

  1. Compute ConfidenceScore from ValidationResult (5-signal weighted sum)
  2. Detect if file is critical path (auth, crypto, password patterns)
  3. Decide: auto-merge eligible OR requires approval
  4. create_branch() → new branch from base (e.g. fix/a3f9-20240816-142301)
  5. _apply_patch_to_worktree() → write new file content to disk
  6. commit_changes() → git add -A && git commit -m "title"
  7. push_branch() → inject GitHub token into remote URL → git push
  8. create_pull_request() → GitHub API → returns PR URL
  9. restore_worktree() → checkout back to base branch regardless of success/failure

LLM-generated PR description includes:

  • 2–3 sentence professional summary (via Haiku triage call)
  • Issues addressed table with root causes
  • Confidence score breakdown table
  • Unified diff in a code block
  • Auto-merge eligible OR 🔒 Human approval required badge
Key safety design: restore_worktree() runs in a finally block, so even if the push fails, the local repo is always put back to the base branch. This prevents state leaking between consecutive PRs.

Surgical Patcher — SEARCH/REPLACE Mechanics

The patcher (backend/utils/patcher.py) is what makes the system reliable. Instead of asking the LLM to regenerate entire files (which leads to hallucinations and huge diffs), we force it to output anchored edits — each edit must exactly match a unique snippet in the existing file.

The Format

### FILE: backend/utils/db.py
<<<<<<< SEARCH
def execute_query(sql, params):
    cursor.execute(f"SELECT * FROM users WHERE id={params['id']}")
    return cursor.fetchall()
=======
def execute_query(sql, params):
    cursor.execute("SELECT * FROM users WHERE id=?", (params['id'],))
    return cursor.fetchall()
>>>>>>> REPLACE

The LLM can output multiple blocks in one response. Each block can target a different file (for cross-file root-cause fixes).

🔒 Safety Rules (enforced in apply_edits())

RuleWhyWhat happens if violated
SEARCH must match exactly once Prevents ambiguity — we need to know WHICH occurrence to replace Edit is rejected with error: "SEARCH text is ambiguous — matches N places"
SEARCH must exist in file LLM might hallucinate the current code Edit is rejected: "SEARCH text not found"
Changed lines ≤ 60% of file Prevents whole-file rewrite mode (LLM failure case) Entire patch rejected: "changes 73% of file — likely full-file rewrite"
At least one edit must apply Empty patches are useless PatchResult.ok = False

Flexible Matching

If exact match fails, the patcher tries whitespace-flexible matching — each line is right-stripped before comparison. This handles cases where the LLM got trailing spaces slightly wrong but the anchor is otherwise correct. The flexible matcher still requires a unique match.

Cross-File Patches

The Code Generator can edit multiple files in one response via ### FILE: path markers:

### FILE: backend/utils/db.py
<<<<<<< SEARCH
...fix symptom...
>>>>>>> REPLACE

### FILE: backend/utils/auth.py
<<<<<<< SEARCH
...fix root cause...
>>>>>>> REPLACE

The patcher groups edits by file using parse_file_edits(), then applies them independently. The final PatchResult contains a FilePatch for each modified file.

Interview answer: "We use anchored SEARCH/REPLACE instead of whole-file generation because LLMs hallucinate when regenerating large files. By forcing the LLM to copy an exact snippet from the existing code, we guarantee the edit targets the right location. If the LLM hallucinates the current code, the SEARCH won't match and the edit is rejected atomically — no partial corruption."

Every pull request gets a ConfidenceScore computed from 5 weighted signals. The score determines whether the PR can auto-merge or needs human review.

ChromaDB Memory Layer

The system has a semantic memory of past validated fixes stored in ChromaDB (backend/utils/chroma_memory.py). When investigating a bug, it searches for similar past fixes and uses them to boost confidence.

What Gets Stored

After a fix passes all 4 validation gates AND the PR is successfully created, RepositoryMemory.store_fix() is called with:

  • bug_type — the issue class (functional_bug, security_vulnerability, etc.)
  • root_cause — why the bug existed
  • fix_strategy — what was changed to fix it
  • affected_file — the epicenter file
  • confidence_score — the final confidence
  • validation_summary — which gates passed
  • repo_key — the repository name (scopes memory per repo)

The embedding text sent to ChromaDB: "Issue type: {bug_type}. Root cause: {root_cause}. Validated fix: {fix_strategy}"

Document ID (deduplication)

Each fix gets a stable ID: sha256(repo_key | bug_type | file | root_cause)[:24]. This means if the same bug is fixed again (e.g. you re-run the pipeline), the memory is updated (upsert), not duplicated.

Query During Investigation

Bug Investigation Agent calls query_similar(bug_type, code_snippet, repo_key). ChromaDB returns the top 3 most similar past fixes (cosine similarity ≥ 0.85). If any match, they're attached to Finding.similar_past_fixes and the confidence scorer awards +15%.

Why this matters: If you fix a SQL injection bug in db.py, then later discover a similar SQL injection in api.py, the memory layer will surface the db.py fix as a reference. The Code Generator sees it in the prompt context ("here's a similar fix that worked before") and the confidence score gets a boost because you're repeating a known-good pattern.
Graceful degradation: ChromaDB imports numpy, which can fail on Windows with locked-down security policies. If the import fails, RepositoryMemory.__init__() sets self.collection = None and all store/query methods become no-ops. The pipeline runs normally without memory — it just can't earn the cache-hit signal.

LLM Client — Tiered Models + Aerolink Proxy

The LLMClient (backend/utils/llm_client.py) wraps the Anthropic SDK with retry logic and tiered model selection.

Model Tiers

TierModel (configurable)Used forCost per 1M tokens
haiku claude-haiku-4-5-20251001 Triage, JSON extraction, PR summaries ~$0.40 input / $2.00 output
sonnet claude-sonnet-4-6 Bug confirmation, root-cause analysis, code generation ~$3.00 input / $15.00 output

Actual pricing depends on the Anthropic API tier or proxy. Aerolink uses credit-based pricing.

Retry Logic

Exponential backoff with jitter: delay = base_delay * (2 ** attempt) + random(0, 1). Default: 4 retries, 1-second base delay.

Non-retryable errors (fail fast):

  • BadRequestError (400) — malformed request
  • AuthenticationError (401) — bad API key
  • PermissionDeniedError (403) — blocked by proxy
  • NotFoundError (404) — bad model name

Retryable errors:

  • Rate limits (429)
  • Overloaded (529)
  • Timeouts
  • Network errors

🔧 The Aerolink User-Agent Fix

This project uses Aerolink as an Anthropic-compatible proxy (cheaper credits). Aerolink's WAF blocks any request whose User-Agent header contains "Anthropic/Python".

Problem: The Anthropic SDK (anthropic 0.111.0) always prepends its own identifier to the User-Agent, producing headers like:

User-Agent: Anthropic/Python 0.111.0, python-httpx/0.28.1

Setting default_headers={"user-agent": "..."} doesn't work — the SDK concatenates its UA with yours.

Solution: We subclass httpx.AsyncHTTPTransport and override handle_async_request() to replace the header at the lowest layer:

class _StripAnthropicUATransport(httpx.AsyncHTTPTransport):
    async def handle_async_request(self, request: httpx.Request):
        request.headers["user-agent"] = "python-httpx/0.28.1"
        return await super().handle_async_request(request)

Then pass this transport when creating the client:

self.client = anthropic.AsyncAnthropic(
    api_key=settings.anthropic_api_key,
    base_url=settings.anthropic_base_url,
    http_client=httpx.AsyncClient(transport=_StripAnthropicUATransport())
)
Interview tip: "We ran into an issue where Aerolink's firewall blocked the Anthropic SDK's default User-Agent. I traced the issue through the SDK source, found that it concatenates UA headers, and solved it by subclassing httpx's transport layer to replace the header before it hits the wire. This demonstrates debugging third-party SDK internals and working at the HTTP transport level."

🔑 Token Injection for Push

Problem: Pydantic Settings reads .env at import time (when the module loads). But in Streamlit, the user enters their GitHub token in the sidebar after import — so settings.github_token is always None.

Solution 1 — Dynamic token reading:

def _token() -> str | None:
    return os.environ.get("GITHUB_TOKEN") or settings.github_token or None

Read from os.environ at call time, not import time. The sidebar writes os.environ["GITHUB_TOKEN"] when the user types it.

Solution 2 — URL injection before push:

def push_branch(self, repo_path: Path, branch_name: str):
    token = _token()
    if token:
        result = subprocess.run(
            ["git", "remote", "get-url", "origin"],
            cwd=repo_path, capture_output=True, text=True
        )
        remote_url = result.stdout.strip()
        if "github.com" in remote_url and f"{token}@" not in remote_url:
            auth_url = remote_url.replace(
                "https://", f"https://{token}@", 1
            )
            subprocess.run(
                ["git", "remote", "set-url", "origin", auth_url],
                cwd=repo_path, check=True, capture_output=True
            )
    subprocess.run(["git", "push", "-u", "origin", branch_name], ...)

Before pushing, inject the token into the remote URL so git can authenticate. This happens every time because the cloned repo starts with a tokenless URL.

Interview answer: "We had a chicken-and-egg problem: Pydantic Settings loads configuration at import time, but Streamlit collects the GitHub token at runtime. I solved it by making the token reader check os.environ dynamically at call time, and injecting the token into the git remote URL right before each push. This avoids storing credentials in config files."

Streamlit UI — Architecture & Live Feed

The UI (streamlit_app.py) is a single-page Streamlit app. It runs the entire orchestrator pipeline in a background thread and streams events live to the main UI thread via queue.Queue.

Threading Model

Main Thread (Streamlit) Background Thread │ │ │ User clicks "▶ Run" │ ├──────────────────────────────────────▶ threading.Thread.start() │ │ async orchestrator.run_pipeline() │ │ │ while True: │ │ event = queue.get(timeout=0.2) │ │ ├─ emit(PipelineEvent) → queue.put() │ ├─ emit(PipelineEvent) → queue.put() │ if event is _DONE: break ├─ emit(PipelineEvent) → queue.put() │ │ │ │ queue.put(_DONE) │ └─ thread exits

Key insight: Streamlit's main thread must stay free to re-render the UI. If we called asyncio.run() directly on the main thread, the UI would freeze for 2 minutes. The background thread + queue pattern lets us update the UI incrementally as events arrive.

Live Feed Implementation

The feed uses st.empty() placeholders that get rewritten on every loop iteration:

feed_box = st.empty()
card_htmls = []

while True:
    event = event_queue.get(timeout=0.2)
    if event is _DONE:
        break
    card_htmls.append(_feed_card_html(event))
    feed_box.markdown(
        '
' +
        "".join(reversed(card_htmls[-50:])) +  # newest first, cap at 50
        '
',
        unsafe_allow_html=True
    )

Session State for Persistence

After a run completes, the PipelineJob is stored in st.session_state["last_job"]. This lets Streamlit re-render the results tabs across page refreshes without re-running the pipeline.

Complete Pipeline Flow — Step by Step

Here's the exact sequence when you click "▶ Run full analysis":

1

User Input

Sidebar: repo URL (https://github.com/owner/repo), branch (main), Anthropic API key, GitHub token (optional).

2

Environment Setup

Streamlit writes os.environ["ANTHROPIC_API_KEY"] and os.environ["GITHUB_TOKEN"]. Backend imports can now see them.

3

Job Creation

Create PipelineJob(repo_url, repo_owner, repo_name, branch). Status starts at PENDING.

4

Background Thread Launch

threading.Thread(target=_run_pipeline_in_thread, args=(job, event_queue)) starts. Main thread enters polling loop.

5

Clone Repository

job.status = CLONING. git clone --depth=1 --branch=main {url} {tmpdir}/repo. Creates temp directory via tempfile.mkdtemp().

6

Phase 1 — Discovery

job.status = PHASE_1_DISCOVERY. Run agents 1–4 in sequence:

  1. Repo Mapper: build KnowledgeGraph (4 passes), emit syntax error findings
  2. Dependency Analyzer: check pip/npm dependencies
  3. Static Analysis: run Bandit/ESLint if available
  4. LLM Bug Hunter: Stage A (Haiku triage all files) → Stage B (Sonnet confirm candidates)

Result: job.findings populated with discovered bugs.

7

Phase 2 — Investigation

job.status = PHASE_2_INVESTIGATION. For each finding:

  • Call kg.analyze_change() → impact paths
  • Call kg.blast_radius() → affected file count
  • Query ChromaDB for similar past fixes
  • If no root_cause yet: LLM call to generate one

Result: findings enriched with blast_radius, impact_paths, similar_past_fixes.

8

Phase 3 — Planning

job.status = PHASE_3_PLANNING. Repair Planner groups findings by file, orders by dependency depth (dependencies first), prioritizes security > high severity > wide blast radius.

Result: job.repair_plan with ordered RepairPlanItems.

9

Phase 4 — Fix & Validate (loop over plan items)

job.status = PHASE_4_FIX_VALIDATE. For each RepairPlanItem:

  1. Code Generation: LLM generates SEARCH/REPLACE patch → PatchResult
  2. If patch.ok is False: retry up to 3 times with error feedback
  3. Validation Agent: apply patch to sandbox, run 4 gates → ValidationResult
  4. Security Verification: Bandit on patched files → sets gate_4
  5. Compute ConfidenceScore from validation + memory hit + fix order
  6. If all gates passed: proceed to publication
  7. Else: mark as unresolved, continue to next item
10

Phase 5 — Publication (per validated fix)

job.status = PHASE_5_PUBLICATION. PR Author:

  1. Create branch: fix/{finding_id}-{timestamp}
  2. Write patch files to working tree
  3. Commit with LLM-generated title
  4. Push to GitHub (with token injection)
  5. Create PR via GitHub API
  6. Store validated fix in ChromaDB
  7. Restore worktree to base branch

Result: job.pull_requests contains PR objects with GitHub URLs.

11

Completion

job.status = COMPLETED. Queue receives _DONE sentinel. Background thread exits. Main thread renders final results tabs.

12

Cleanup

finally: block: gc.collect(), time.sleep(0.5), shutil.rmtree(tmpdir) (Windows-safe temp cleanup).

Bugs We Fixed — Technical Deep Dive

During development and deployment, we encountered 5 major bugs. Here's what went wrong and how we fixed each one.

🐛 Bug #1: Windows Temp Directory Cleanup — PermissionError [WinError 32]

Symptom:

PermissionError: [WinError 32] The process cannot access the file because
it is being used by another process: '...\\.git\\objects\\...'

Root Cause:

On Windows, when you git clone a repository, git.exe spawns background processes that keep file handles open on .git/objects files. Python's with tempfile.TemporaryDirectory(): tries to delete the directory immediately when the context exits, but Windows refuses because the handles are still open.

The Fix:

  1. Replace with tempfile.TemporaryDirectory(): with manual tmpdir = tempfile.mkdtemp()
  2. In the finally: block, add gc.collect() to force Python to close any file handles it's holding
  3. Add time.sleep(0.5) to let git processes finish
  4. Try shutil.rmtree(tmpdir, ignore_errors=False)
  5. If that fails, sleep 1 more second and retry with ignore_errors=True
tmpdir = tempfile.mkdtemp()
try:
    repo_path = github.clone_repo(...)
    # ... pipeline ...
finally:
    gc.collect()
    time.sleep(0.5)
    try:
        shutil.rmtree(tmpdir, ignore_errors=False)
    except Exception:
        time.sleep(1.0)
        shutil.rmtree(tmpdir, ignore_errors=True)

Applied to: backend/agents/orchestrator.py and streamlit_app.py (the repo map builder)

🐛 Bug #2: Aerolink Proxy Blocking User-Agent

Symptom:

anthropic.PermissionDeniedError: Error code: 403
Your request was blocked by our security system.

Root Cause:

Aerolink's WAF blocks any request with "Anthropic/Python" in the User-Agent header. The Anthropic SDK version 0.111.0 always prepends "Anthropic/Python 0.111.0" to the UA — even if you set custom headers, it concatenates them.

Failed Attempt:

self.client = anthropic.AsyncAnthropic(
    api_key=key,
    base_url=proxy_url,
    default_headers={"user-agent": "python-httpx/0.28.1"}  # doesn't work!
)

The SDK still sends: User-Agent: Anthropic/Python 0.111.0, python-httpx/0.28.1

The Fix:

Subclass httpx.AsyncHTTPTransport and intercept the request at the lowest layer before it goes out:

class _StripAnthropicUATransport(httpx.AsyncHTTPTransport):
    async def handle_async_request(self, request: httpx.Request):
        request.headers["user-agent"] = "python-httpx/0.28.1"
        return await super().handle_async_request(request)

self.client = anthropic.AsyncAnthropic(
    api_key=settings.anthropic_api_key,
    base_url=settings.anthropic_base_url,
    http_client=httpx.AsyncClient(transport=_StripAnthropicUATransport())

Applied to: backend/utils/llm_client.py

🐛 Bug #3: Wrong Environment Variable Names

Symptom:

LLM calls still blocked by Aerolink even after UA fix. Model name was falling back to defaults instead of using the .env values.

Root Cause:

The .env file used incorrect variable names that didn't match the Pydantic field names:

# ❌ WRONG (these are ignored by Pydantic)

🐛 Bug #4: GitHub Token Not Reaching GitHubClient

Symptom:

subprocess.CalledProcessError: Command ['git', 'push'] returned non-zero
exit status 128
stderr: remote: Permission to owner/repo.git denied to ...

Root Cause:

Two issues stacked:

  1. Pydantic import-time freeze: settings = Settings() runs when config.py is imported (at module load). The Streamlit sidebar hasn't run yet, so GITHUB_TOKEN isn't in os.environ. Result: settings.github_token = None forever.
  2. Token not in git remote URL: Even if we had the token, the cloned repo's remote URL was https://github.com/... without auth. Git push would prompt for credentials (which fails in non-interactive mode).

The Fix (Part 1 — Dynamic Token Reading):

def _token() -> str | None:
    """Read GitHub token at call time, not import time."""
    return (
        os.environ.get("GITHUB_TOKEN")  # Streamlit writes this
        or settings.github_token         # .env fallback
        or None
    )

The Fix (Part 2 — URL Injection Before Push):

def push_branch(self, repo_path: Path, branch_name: str):
    token = _token()
    if token:
        result = subprocess.run(
            ["git", "remote", "get-url", "origin"],
            cwd=repo_path, capture_output=True, text=True
        )
        remote_url = result.stdout.strip()
        if "github.com" in remote_url and f"{token}@" not in remote_url:
            # Inject token: https://github.com/... → https://TOKEN@github.com/...
            auth_url = remote_url.replace("https://", f"https://{token}@", 1)
            subprocess.run(
                ["git", "remote", "set-url", "origin", auth_url],
                cwd=repo_path, check=True, capture_output=True
            )
    # Now push will authenticate
    subprocess.run(["git", "push", "-u", "origin", branch_name], ...)

Applied to: backend/utils/github_client.py

🐛 Bug #5: PRs Not Appearing on GitHub (Permissions)

Symptom:

Push succeeds, but create_pull_request() returns an error or PR doesn't appear on GitHub.

Root Cause:

The test repo andela/buggy-python is not owned by the user. You can't open PRs on repos you don't have write access to.

The Fix:

This isn't a code bug — it's expected behavior. The solution is to fork the repository first, then run the analysis against your fork. The PR will then appear on your fork and you can open an upstream PR manually if desired.

Status: Documented as expected behavior. User accepted this.

What this demonstrates: Systematic debugging (logs → hypothesis → trace SDK source → test fix), handling platform-specific issues (Windows file locking), understanding third-party library internals (Anthropic SDK UA concatenation), and config management patterns (Pydantic Settings import-time vs runtime).

Interview Q&A Cheat Sheet

Memorise these answers. They cover the most common technical interview questions about this project.

Q: Walk me through the system architecture at a high level.

"It's a 5-phase multi-agent pipeline. Phase 1 (Discovery): we build a NetworkX knowledge graph from Python AST parsing, then use a tiered LLM approach — Haiku triages all files cheaply, Sonnet confirms real bugs with evidence. Phase 2 (Investigation): we enrich each finding with cross-file blast radius using graph traversal and query ChromaDB for similar past fixes. Phase 3 (Planning): group findings by file and order by dependency depth. Phase 4 (Fix & Validate): generate SEARCH/REPLACE patches with Sonnet, validate through 4 gates — AST syntax, pytest, regression suite, and Bandit security scan. Phase 5 (Publication): commit to a new branch, push to GitHub with token injection, and open a PR via the GitHub API. The entire flow runs in a background thread with live event streaming to a Streamlit UI via queue.Queue."

Q: Why did you choose NetworkX for the knowledge graph instead of a graph database like Neo4j?

"NetworkX is an in-memory Python library that's fast for small-to-medium repos (under 10K files). We rebuild the graph from scratch on each run anyway, so we don't need persistence. NetworkX gives us BFS/DFS out of the box for blast radius calculations, and it integrates naturally with the Python AST data structures. A graph DB would add deployment complexity (running a separate database server) for a use case that doesn't need it."

Q: How does the knowledge graph help with bug detection?

"The graph tracks IMPORTS, CALLS, and TESTS edges between files and functions. When we find a bug in db.py, we traverse the graph backwards (against the import direction) to find all consumers — this tells us the blast radius. We also use it to fetch related files as context for the LLM: if db.py imports auth.py and is imported by api.py, we send those files to the LLM so it can see the full contract and verify the bug is real, not just a local oddity. The graph also detects circular dependencies and finds related tests automatically."

Q: Why use two LLM tiers (Haiku + Sonnet) instead of just one model?

"Cost and speed. If we sent every file to Sonnet, a 100-file repo would cost ~$1.50 in LLM calls. With the two-stage pipeline, Haiku does a cheap triage pass at $0.001/file to flag candidates, then we only send files with candidates to Sonnet for deep verification. This cuts cost by 80% and runtime by 60% while maintaining the same accuracy — because Haiku is good enough to spot suspicious patterns, and Sonnet confirms whether they're real."

Q: What's the SEARCH/REPLACE patching system and why not just regenerate the whole file?

"LLMs hallucinate when asked to regenerate entire files — they drop imports, change unrelated code, and produce huge diffs that are hard to review. SEARCH/REPLACE forces the LLM to anchor each edit to an exact snippet from the current file. If the SEARCH text doesn't match exactly once, the edit is rejected atomically. This guarantees minimal diffs (only the lines that need to change) and prevents the LLM from drifting off into hallucination mode. We also have a sanity check: if more than 60% of the file changes, we reject it as a likely whole-file rewrite."

Q: How do you handle cases where the repository has no test suite?

"We detect this by looking for pytest config files and test_*.py files. If there are none, we set tests_available=False and skip gates 2 & 3. The patch can still be published — gate 1 (AST syntax) must pass, and if Bandit is available we run it. But the confidence score is capped at 60%, which forces the PR to be created as a draft requiring human approval. This prevents us from auto-merging changes that couldn't be validated by tests."

Q: Explain the confidence scoring system.

"It's a weighted composite of 5 signals: tests passed (40%), security clean (25%), AST valid (10%), cache hit (15%), and fix order (10%). Tests are the strongest signal because they prove the patch doesn't break existing behavior. Security is next because a fix that introduces a vulnerability is worse than no fix. If the score is 70% or higher and it's not critical path code, the PR is eligible for auto-merge. Below 70% or if it touches auth/crypto patterns, it requires human approval."

Q: What was the hardest bug you encountered and how did you fix it?

"The Aerolink User-Agent blocking. Symptoms: all LLM calls were returning 403 Forbidden. I checked the network logs and saw the proxy was rejecting requests with 'Anthropic/Python' in the User-Agent. I tried setting default_headers in the SDK, but it still failed — turned out the SDK concatenates its own UA with yours. I read the anthropic SDK source, found it uses httpx under the hood, and realized I could subclass AsyncHTTPTransport to intercept the request before it's sent. I overrode handle_async_request() to replace the User-Agent header at the lowest layer. That fixed it. This demonstrates debugging third-party libraries at the HTTP transport level."

Q: How does ChromaDB memory improve the system?

"ChromaDB stores embeddings of past validated fixes — the bug type, root cause, and fix strategy. When investigating a new bug, we query ChromaDB for semantically similar past fixes in the same repo. If we find a match with cosine similarity ≥ 0.85, it means we've fixed something similar before. The Code Generator sees this as context ('here's a fix that worked last time') and the confidence scorer adds 15% because we're repeating a known-good pattern. It also prevents duplicate fix attempts — the document ID is a hash of (repo, bug_type, file, root_cause), so re-running the pipeline on the same bug updates the existing memory entry instead of creating duplicates."

Q: Why Streamlit instead of a React frontend + FastAPI backend?

"Speed of iteration. Streamlit lets you build an interactive UI with live updates in pure Python — no separate frontend/backend split, no API contracts to maintain. The live feed is implemented with st.empty() placeholders that get rewritten on every event. The tradeoff is we're tied to Streamlit's component model and single-process architecture, but for a proof-of-concept that's acceptable. In production you'd probably want FastAPI + React + WebSocket for the live feed, but Streamlit gets you 80% of the way there in 20% of the code."

Q: What would you improve if you had more time?
Answers (pick 2-3):
  • Parallel agent execution: Right now agents run sequentially. We could parallelize Phase 1 discovery (run LLM Bug Hunter on chunks of files concurrently) to cut runtime from 2min to under 1min.
  • Better C/C++ support: Currently we only parse #include directives with regex. Full clang AST parsing would give us function-level call graphs for C/C++ like we have for Python.
  • Multi-repo learning: Right now ChromaDB memory is scoped per repo. We could have a global memory pool that learns patterns across all repos a user has analyzed.
  • Incremental graph updates: Rebuild the graph from scratch every run. For large repos, we could cache the graph and only update changed files.
  • Confidence signal tuning: The 40/25/10/15/10 weights are somewhat arbitrary. We could tune them with ML on a corpus of accepted vs rejected PRs.
Final tip: Practice explaining the 30-second elevator pitch out loud. Interviewers often start with "tell me about this project" — nail that and you set the tone for the rest of the conversation.
